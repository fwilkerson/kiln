# 2026-11-08: tui-test and a pseudo-terminal inside a kiln session's sandbox

Question: can the audit drive a TUI with tui-test inside the sandbox kiln gives every session? Spec 3 gives the audit
Bash and tui-test for this.

## The run

One audit session, started through `claude.Run` with what `build.sandboxed` and `build.audit` give it: tools Read,
Grep, Glob and Bash; kiln's deny rules and forbidden sentences; writes to the tree and Go's caches; the Go proxy's
domains. `.claude/settings.json` allowed `Bash(tui-test *)`. tui-test 0.1.1 was on `PATH`, installed with prov. The
session was asked to drive `docs/research/tui/prototypes/bubbletea` at 100 × 30 and 60 × 16. It ran 35 turns for
$1.53, and left the tree as it found it.

| Command                                              | Result, word for word                                                                             |
|------------------------------------------------------|---------------------------------------------------------------------------------------------------|
| `tui-test --session bt100 open --cols 100 --rows 30` | `failed to start daemon: Operation not permitted (os error 1)`                                    |
| the same, with `TUI_TEST_HOME=$TMPDIR/tui-test-home` | `failed to start daemon: daemon did not become ready: socket never started accepting connections` |
| `go test ./e2e` (termtest, `pty.StartWithSize`)      | `e2e_test.go:73: operation not permitted`                                                         |
| `go build`, `go test ./bubbletea`                    | worked                                                                                            |

With no terminal to drive, the audit sent the model the same messages the prototype's tests send, saved 19 screens as
PNG through termtest's emulator, and read them. It reported four real faults the research had partly found by eye: a
screen 18 lines tall in 16 rows, a detail page drawn past column 60, a table cell cut mid-number, and the wheel
switching the open build. It could not see key and mouse decoding, the real renderer, or a real resize.

## Why: no pseudo-terminal in the sandbox

A sandboxed command cannot open a pseudo-terminal. Two Haiku sessions, sandboxed with `allowUnsandboxedCommands:
false` as kiln's are, each ran `python3 -I -c "import os; print(os.openpty())"`:

| `sandbox.allowPty` in `--settings` | Result                                               |
|------------------------------------|------------------------------------------------------|
| `false`                            | `PermissionError: [Errno 1] Operation not permitted` |
| `true`                             | `PermissionError: [Errno 1] Operation not permitted` |

The sandbox runtime has the switch: `anthropics/sandbox-runtime`'s macOS profile adds `(allow pseudo-tty)` and
`/dev/ptmx` when its config sets `allowPty` (`src/sandbox/macos-sandbox-utils.ts`). Claude Code's settings reference
lists no such key, and the run above shows Claude Code does not pass it through.

## What follows

- **Only an unsandboxed command can drive a TUI.** `sandbox.excludedCommands` runs a matching command outside the
  sandbox, with no filesystem or network limits. kiln's `--settings` sets `allowUnsandboxedCommands: false`, which
  makes the sandbox admin-required, so Claude Code ignores `excludedCommands` from the project's settings: only
  kiln's own settings can name it. `tui-test run` starts any program it is given, so excluding `tui-test *` lets the
  session run anything unsandboxed.
- **A build session cannot run a termtest acceptance test.** termtest opens a pseudo-terminal, so `go test` on spec
  3's acceptance tests fails inside the session. kiln's gate runs outside any session, so the gate can.
- **In-process screens caught the layout faults.** Sending the model its messages and reading the PNGs found what
  the research found by eye, with no terminal.
