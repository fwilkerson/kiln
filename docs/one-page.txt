::: titleblock
cell id | One developer, one Mac, many agents
wordmark kiln
motto Specs in. Commits out.
para With kiln, agents build the specs you shape, and fix what your checks find on a schedule. kiln runs on your Mac, and commits the work to main.

cell problem | Why kiln
lead **A developer's attention is the scarcest resource on a project.**
para **An agent's tests check what it understood.** Its report of success does not say whether it built what you asked for.
para **An agent waits for a person.** A task starts when someone types it, and a question stops the work until someone answers.
cell answer | With kiln
big When an @agent{agent} gets something wrong, you add a @you{test} or edit its @you{instruction file}.
para **You approve each acceptance test as a Given, a When and a Then.** A build writes it as a test that runs your program as its user would.
para **A build cannot change the commands it must pass.** The gate is that list of commands, and kiln reads it from main. It runs every earlier spec's acceptance tests on each later build.
para **Checks run on a schedule too.** A check can find tests that got slower, an outdated dependency, a CVE, docs that no longer match the code, or new errors in a service's logs. An agent fixes what the check finds, and each bug you file.

cell attn | Where your attention goes
item ●1 | **The spec**: what to build next, and how to tell it is done. `/shape` asks its questions while it drafts the spec with you.
item ●2 | **The checks and instructions**: the gate in `kiln.json`, the checks on a schedule, and each agent's instruction file.
item ●3 | **The result**: try what landed, then accept it or revise the spec.
:::

view 2 BUILD | one spec, from a draft to main | after you approve the spec, a build asks you nothing while it runs

::: swimlane

phase 1 | SHAPE
phase 2 | BUILD, IN THE BACKGROUND

box shape @you 1.1 | **shape a spec** ●1 | `/shape`, then approve
more `/shape` asks you questions, and the project's reviewers read the draft before you approve it. The spec's acceptance tests say what done means, each as a Given, a When and a Then. Once you approve, `/shape` marks the spec Approved, commits it on main and queues it.
box fire @you 1.2 | `kiln fire` | builds each | queued spec
box spec @repo 1.1-2 | 📄 SPEC | approved, on main
arrow shape spec

box build @agent 2.1 | BUILD | the code
box verify @agent 2.1 | VERIFY | a test for each | acceptance test
more Each acceptance test becomes an automated test, which runs your program as its user would. With `"workflow": "build-and-verify"` or `"verify-first"` in `kiln.json`, a second session writes those tests from the spec alone, and never reads the build session's work. kiln proves they fail on main before the build session reads them. `"build-and-verify"` starts both sessions at once, and `"verify-first"` starts the build session once the tests are proved. With `"workflow": "build"`, the default, one session writes the code and the tests.
box gate @kiln 2.2 | GATE ●2 | your checks, | read from main
more kiln reads the gate's commands from main, never from the build's checkout, so a build cannot weaken the checks it is held to.
box audit @agent 2.3 | AUDIT | a second session | reads the work
more A failing gate sends the work back to the build session, as a round. The audit's findings go back too, and spend no round. Detail A says what happens when the rounds run out.
arrow fire build
arrow fire verify
arrow build gate
arrow verify gate
arrow gate audit
detail A | build gate audit

box land @kiln 3.1 | LAND | one commit
box main @repo 3.1 | MAIN | code and tests
more The acceptance tests land with the code, and the gate runs them on every later build. A later build that breaks an earlier spec does not land.
box try @you 3.2 | **try it** ●3 | `kiln accept x`
arrow audit land
arrow land main
arrow main try
:::

::: details
detail A | Detail A — when a build cannot land as it is | The build keeps its checkout and sessions, so it can go on.
rung @agent | 1 · Round | the build | A failing gate goes back to the session, for up to 3 rounds by default. Then the build stops.
rung @agent | 2 · Amend | the build | A build that finds the spec wrong writes an amendment, and waits on its branch.
rung @you | 3 · Decide | you ●3 | Accept or reject the amendment. Or run `kiln tend`, repair what stopped in a session of your own, and the build goes on.
:::

parts PARTS LIST | a check or a gauge on a schedule, then an agent's fix
part 1 @kiln | Bugs | a check lists `bugs/`; the fix takes the first report | Fixes each bug you file, one after another, with a test that fails first.
part 2 @kiln | Code health | a gauge scores the Go files | Refactors the three lowest-scoring files, and changes no behavior.
part 3 @kiln | Gate time | a check compares the gate's recent times with the times before | Once the gate takes 50% longer, speeds up the slowest tests, keeps every check, and waits for you.
part 4 @kiln | Docs | a check finds packages whose code changed | Reads their docs against the code, fixes what is false, and waits for you.
part 5 @agent | A fix | a build with no spec | Gated, audited and landed like any build.
:::

view 4 START | what you type | to set a project up, build a spec, and add a monitor

::: spec
column
howto 4.1 | Set a project up | `kiln init` @you
```term
$ kiln init
$ git add .kiln .claude
$ git commit -m "chore: set up kiln"
```
caption `kiln init` writes your checks and the agents' instructions into `.kiln/`, and links `/shape` into `.claude/`. It picks defaults for Go, Python with uv, or TypeScript with npm, by your files.
column
howto 4.2 | Build a spec | `/shape` @you then `kiln fire` @you
```term
$ kiln fire
answer: {ok:landed on main} at {h:3f9c2ab81d0e}
  4.2 min · $0.42 · 3 turns
  next: kiln accept answer
```
caption `kiln tui` shows each session live.
column
howto 4.3 | Add a monitor | `kiln monitor add bugs` @you then `kiln monitor install` @you
```term
$ kiln monitor add bugs
$ git add .kiln/monitors
$ git commit -m "chore: add the bugs monitor"
$ kiln monitor install
```
caption kiln ships `bugs`, `go/deps`, `go/docs` and `go/gate-time`. A monitor is a directory: a check, an agent and `monitor.json`.
:::
