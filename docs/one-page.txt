::: titleblock
cell id | One developer, one Mac, many agents
wordmark kiln
motto Tooling in. Commits out.
para kiln runs Claude Code in the background, on your Mac. It builds the specs you approve, and runs chores on a schedule. So one developer can keep a whole repository moving.

cell problem | How agents get used
lead **You take each task to an agent.**
para You give the agent the work, watch it run, check the result, and give it the next task.
para What if you built the system instead, and the agents worked inside that system?

cell answer | With kiln
big You shape the @you{specs} and build the tooling; kiln runs the @agent{agents} inside that tooling.
para **Specs become commits.** One session can write the code, and another the tests, from the spec alone. Work that passes your checks and an audit lands on main.
para **Your checks decide.** kiln reads them from main, so no build can weaken them.
para **kiln runs on itself.** Monitors do kiln's own chores on a schedule. View 3 shows four of them.

cell attn | Where your time goes
item ●1 | **Ideas**: what to build next, shaped into a spec with `/shape`.
item ●2 | **The system**: the gate, the monitors and the agents' instructions that every build follows.
item ●3 | **The product**: try what landed, and decide what comes next.
:::

view 2 BUILD | one spec, from a draft to main | after you approve it, no one waits at the keyboard

::: swimlane
lane @you | the developer

phase 1 | SHAPE
phase 2 | BUILD, IN THE BACKGROUND

box shape @you 1.1 | **shape a spec** ●1 | `/shape`, then approve
more `/shape` asks you questions, and the project's reviewers read the draft before you approve it. The spec's acceptance tests say what done means, each as a Given, a When and a Then. Once you approve, `/shape` marks the spec Approved, commits it on main and queues it.
box fire @you 1.2 | `kiln fire` | builds each | queued spec
box spec @repo 1.1-2 | 📄 SPEC | approved, on main
arrow shape spec

box build @agent 2.1 | BUILD | the code
box verify @agent 2.1 | VERIFY | the tests, from | the spec alone
more With testSession on, two sessions work in two clones. One writes the code, and the other writes the acceptance tests. Neither session reads the other's work. Without testSession, one session writes both.
box gate @kiln 2.2 | GATE ●2 | your checks, | read from main
more kiln reads the gate's commands from main, never from the build's checkout, so a build cannot weaken the checks it is held to.
box audit @agent 2.3 | AUDIT | a second session | reads the work
more A failing gate sends the work back to the build session, as a round. The audit's findings go back too, and spend no round. Detail A says what happens when the rounds run out.
arrow fire build
arrow fire verify
arrow build gate
arrow verify gate
arrow gate audit
detail A | build gate audit

box land @kiln 3.1 | LAND | one commit
box main @repo 3.1 | MAIN
box try @you 3.2 | **try it** ●3 | `kiln accept x`
arrow audit land
arrow land main
arrow main try
:::

::: details
detail A | Detail A — when a build cannot land as it is | The build keeps its checkout, so you can ask its session why.
rung @agent | 1 · Round | the build | A failing gate goes back to the session, for up to 3 rounds by default. Then the build stops.
rung @agent | 2 · Amend | the build | A build that finds the spec wrong writes an amendment, and waits on its branch.
rung @you | 3 · Decide | you ●3 | Accept or reject the amendment. Or fix main or the spec, and queue the spec again.
:::

view 3 AUTOMATE | what monitors and gauges could do | four of the monitors kiln runs on its own repository

::: assembly
box launchd @kiln A2-A3 | LAUNCHD | `kiln monitor run`, | each hour
group monitors B1-B4 | MONITORS, FOR EXAMPLE ●2
box bugs @kiln B1 | BUGS {1} | every hour
box health @kiln B2 | CODE HEALTH {2} | every day
box gate-time @kiln B3 | GATE TIME {3} | every day
box docs @kiln B4 | DOCS {4} | every day
box fix @agent C2-C3 | A FIX {5} | a session with | the monitor's | own agent
valve gate @kiln | GATE
rail main @repo D1-D4 | MAIN
arrow launchd monitors
arrow monitors fix
arrow fix main via gate

parts PARTS LIST | a check or a gauge on a schedule, then an agent's fix
part 1 @kiln | Bugs | a check lists `bugs/`; the fix takes the first report | Fixes each bug you file, one after another, with a test that fails first.
part 2 @kiln | Code health | a gauge scores the Go files | Refactors the three lowest-scoring files, and changes no behavior.
part 3 @kiln | Gate time | a check compares the gate's recent times with the times before | Once the gate takes 50% longer, speeds up the slowest tests, keeps every check, and waits for you.
part 4 @kiln | Docs | a check finds packages whose code changed | Reads their docs against the code, fixes what is false, and waits for you.
part 5 @agent | A fix | a build with no spec | Gated, audited and landed like any build.
:::

::: spec

howto 4.1 | Set a project up | `kiln init` @you
```term
$ kiln init
wrote .kiln/kiln.json
linked .claude/skills/shape
{q:commit .kiln/ on main: kiln reads it there}
```
caption The preset follows your files: `go`, `python` for uv, or `typescript` for npm.
column
howto 4.2 | Build a spec | `/shape` @you then `kiln fire` @you
```term
$ kiln fire
answer: {ok:landed on main} at {h:3f9c2ab81d0e}
  4.2 min · $0.42 · 3 turns
  next: kiln accept answer
```
caption `kiln tui` shows each session live.
column
howto 4.3 | Add a monitor | `kiln monitor add bugs` @you then `kiln monitor install` @you
```term
$ kiln monitor add bugs
wrote .kiln/monitors/bugs/agent.md
wrote .kiln/monitors/bugs/check
wrote .kiln/monitors/bugs/monitor.json
{q:commit .kiln/monitors/bugs/ on main: kiln reads it there}
```
caption kiln ships `bugs`, `go/deps`, `go/docs` and `go/gate-time`. A monitor is a directory: a check, an agent and `monitor.json`.
:::
